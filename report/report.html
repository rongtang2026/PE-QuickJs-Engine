1　方法与可复现性

环境

  • JDK 17 (Temurin 17.0.13+11)、apktool 2.11.1、python 3.13（自写 ELF 字符串提取脚本）
  • jadx 1.5.1 未能产出结果：本机 Java 26 与 JDK 17 下均加载 303 个类后静默退出，故 Java 层证据取自 apktool 的 smali 反汇编
# 清单与资源

# dex -> smali（jadx 不可用时的替代路径）

# native 字符串

方法学限制
① 未做动态分析（未安装运行），全部为静态取证。
② “文件不存在”属推断：基于 .so 内残留的 .hx 路径字符串。Haxe 会为每个参与的类保留源文件名与符号，但空类或纯类型别名可能被误判。关键结论（Lua 运行时移除）已用独立证据交叉验证（lua_* C 符号为 0）。
③ smali 可读性低于 Java，但足以定位 API 调用与常量。

5　脚本层：名字是 Lua 的，引擎是 JS 的

5.1　Lua 确实被拔了

Lua 运行时被物理移除，不是“隐藏开关”或“保留但禁用”。

5.2　但 API 名全留着

从上游 source/psychlua/*.hx 提取 add_callback(lua, "name", ...) / .set("name", ...) 注册的函数名共 215 个；本 APK 中按原名存在 211 个（98%）。缺的 4 个是：

getHits / getMisses / getGlobalFromScript / setGlobalFromScript

psychlua.FunkinJS 暴露 124 个方法，注册器按域切分：

registerCoreFunctions      registerGameFunctions     registerGameFunctions2
registerInputFunctions     registerMenuFunctions     registerFileFunctions
registerBackendFunctions    registerAnimateFunctions

连 psychlua.FunkinJS.initLuaShader 这种名字里带 Lua 的方法也保留着。

结论：所谓“对 Lua 的兼容”，是函数名兼容，不是脚本兼容。.lua 文件无法直接运行（没有解释器），但把 makeLuaSprite(...) 改写成 JS 语法后可以调用同名实现。这解释了社区反弹为何最大——老 mod 一行都跑不了，学习成本却不降。

5.3　QuickJS 集成是真的

backend/QuickJS.hx 方法名完整保留：

new / eval / call / hasFunction / setGlobal / getGlobal
runPendingJobs / handleNative / onDispatch / boot
encodeResult / encodeArgs / parseResult / close

底层调用 JS_NewRuntime2、JS_Eval、JS_Call、JS_CallConstructor、JS_EvalFunction。版本串：

6　Vulkan：真调了 API，但是旁挂的

6.1　实现深度

libApplicationMain.so 中出现 65 个不同的 vk* 函数，覆盖 instance/device 创建、swapchain、render pass、pipeline、descriptor、command buffer、image 上传、present 全链路：

vkCreateInstance / vkCreateDevice / vkCreateAndroidSurfaceKHR
vkCreateSwapchainKHR / vkAcquireNextImageKHR / vkQueuePresentKHR
vkCreateRenderPass / vkCreateGraphicsPipelines / vkCmdDraw
vkCmdCopyBufferToImage / vkUpdateDescriptorSets / vkQueueSubmit

但这套实现有明显边界：

  • 没有深度附件、没有 MSAA、多 render pass，vkCmdBeginRenderPass 只有一对
  • 贴图槽硬上限 47，日志原文：[VulkanAndroid] texture slots are full (47), further sprites will not be drawn
  • 引擎自己的说明：OpenGL keeps running underneath until the Vulkan path fully replaces it —— Vulkan 是覆盖层，OpenGL 仍在跑
  • 切换前有独立警告页 substates/VulkanWarningSubState，文案 The Vulkan renderer is still experimental.

6.2　Java 侧的 “VulkanSurfaceHelper” 其实是 Canvas 文字层

该类 6,249 行 smali、57 个方法，但不含任何 OpenGL/EGL/Vulkan API 调用（android/opengl、javax/microedition/khronos、libvulkan 命中均为 0）。实际工作是：

Canvas.drawText ×4        Paint.setTextSize / setColor / setShadowLayer
Typeface.DEFAULT_BOLD     Bitmap.createBitmap / setPixel / getPixels / recycle

即管理一个 SurfaceView，把游戏 Surface 交给 native，同时用 Canvas 画 HUD 文字与诊断信息。native 通过 nativePushTextQuad、nativeSetHudValues、nativeGetHudLine 与之通信。

判定：issue 中“Vulkan 后端完整度不达 3%”是夸张修辞。实际是一个可运行的最小 2D Vulkan 渲染器 + OpenGL 兜底，能画场景、角色、音符、HUD，但受 47 贴图槽与单 pass 限制，离“替换渲染后端”还有距离。

7　完整性校验：闭源之外还有防改

DingLing/pe/QuickJs/Engine/Qz7（18.5KB smali）做了三件事：

  • b()/c()/d() 取 PackageInfo、读签名（GET_SIGNATURES）
  • 遍历 ZIP 条目（classes*.dex、assets/、lib/、res/、META-INF/、AndroidManifest.xml、resources.arsc），用 SHA-256 逐项摘要，与内嵌 32 字节表比对（v()[B、a(I)I 按下标取 4 字节大端）
  • okRoot(String) / okSo(String) —— 检查 root 痕迹与 so 是否存在

对应 Haxe 侧 backend/Qz7r.hx（字段 k/_f/_v/_w/_c/_m/_z，方法 boot，属性 scriptsAllowed）。失败文案：

This copy of the game was modified or re-signed.

含义：改包名、去 dex、换 so、重签名都会命中；命中后 scriptsAllowed 为 false，脚本功能被关。当前包 debuggable=true 且为 debug 签名，说明这是测试构建，不是 r- 正式版。

Apache-2.0 的具体义务

Apache-2.0 允许闭源分发衍生作品，所以“闭源”本身不违约。争议点在第 4 条：

  • §4(a) 向接收者提供本许可证副本 —— 未提供
  • §4(b) 修改过的文件须保留显著修改声明 —— 无
  • §4(c) 保留作品中原有的版权、专利、商标、归属声明 —— 源码层版权头随 Haxe 编译消失，仅剩非正式 credits
  • §4(d) 原作品含 NOTICE 时须附带其内容 —— 未附带
准确表述：闭源合法，但不带许可证副本与归属声明分发不合法。这一点举证成本低、不易反驳，比“抄代码”之类的指控稳。

libvlc 的 LGPL-2.1 另有要求：动态链接、允许替换库、提供许可证与源码获取途径。当前 libvlc.so 作为独立 so 打包（非静态链入 libApplicationMain.so），理论上可替换以满足重链接要求，但许可证文本与书面声明仍然缺失。
